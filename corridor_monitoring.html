Corridor monitoring — how it works

Filters (Year / Month / Apply)

Crossings are not read from Firebase Realtime Database. They come from Google Cloud Storage (awt_data/road_crossings.json) either via a public HTTPS URL to that object, or via the road-crossings-process API (Bearer or Basic auth), which reads the same GCS file server-side. Year and Month restrict which crossings are used by each crossing’s estimated_crossing_time (Unix seconds → calendar date). Apply filter refreshes the map and any active usage view using only crossings that pass the filter.

Hotspot view vs point view

Hotspot view draws a heat layer (density) instead of individual markers. Point view shows a small circle for each crossing. These only apply when Corridor usage is off; in usage mode, crossing markers and the heat layer are hidden so the corridor and band symbology stay readable.

Corridor usage mode

When turned on:

  • Each corridor polygon is filled using a count of filtered crossings whose points fall inside that polygon.
  • Outside-corridor bands summarize crossings that lie outside every corridor (see cluster rules below).
  • The white → red legend is a linear scale: for each feature, intensity is count ÷ maxCount, where maxCount is the largest crossing count among all corridor polygons and among all displayed outside bands (so the red end always matches the busiest visible polygon or band).

Outside clusters and corridor bands (the maths)

  1. Start with each outside-corridor crossing (for the current filter).
  2. Place a 100 m radius buffer (0.1 km) around each crossing point (Turf buffer in kilometers).
  3. Merge buffers that intersect or whose centroids are within ~220 m of each other (pairwise union until stable) so touching or nearly-touching clusters become one polygon.
  4. Count how many filtered crossing points fall inside each merged polygon.
  5. Draw a corridor band only if that count is greater than 2 (i.e. three or more crossings in the cluster). Single and double-crossing clusters are not shown as bands.
  6. For each band shown: take the centroid of the merged buffer polygon. Pick the crossing in that cluster closest to the centroid as the reference point. Find the nearest NG_Roads line segment; the road bearing along that segment defines the road direction. Build a line through the centroid, perpendicular to the road, and extend it 1 km on each side along the ground (rhumb line). Finally, buffer that line by a half-width equal to the maximum distance from the centroid to the boundary of the merged 100 m cluster (distance to each edge segment; the worst case sets the width). That buffered corridor is what you see; crossing counts and colors still refer to points inside the original merged cluster polygon.

Layers (bottom to top)

Satellite basemap → NG_Roads (reference road geometry, bottom vector layer) → corridors / usage fills → outside corridor bands → crossing markers or heat (when usage is off).
